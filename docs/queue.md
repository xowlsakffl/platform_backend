# 비동기 작업 운영 가이드

작성 기준: 2026-07-28

이 문서는 Medi 백엔드의 비동기 작업 기준을 정리한다.

## 1. 기본 원칙

비동기 작업은 사용자 요청 흐름에서 즉시 끝낼 필요가 없거나 외부 시스템 장애와 분리해야 하는 일을 처리한다.

대상 예시:

- 메일 발송
- Push 발송
- 이미지 리사이즈/썸네일 생성
- 엑셀/리포트 생성
- 캐시 무효화 후처리
- 통계/집계 재계산

정합성이 중요한 변경은 먼저 DB transaction과 unique key로 확정한다. 비동기 작업은 알림, 후처리, 재처리 가능한 작업에 사용한다.

## 2. 구현 기준

초기 구현은 아래 중 하나를 선택한다.

| 방식 | 사용 기준 |
| --- | --- |
| DB outbox + scheduler worker | 유실되면 안 되는 작업 |
| Spring `@Async` | 유실되어도 재시도 요구가 낮은 짧은 작업 |
| 외부 queue/stream | 처리량과 retry 정책이 명확히 필요할 때 |

메일, Push, 결제 후처리처럼 유실되면 안 되는 작업은 in-memory `@Async`만으로 처리하지 않는다. 먼저 outbox 또는 delivery 테이블에 저장하고 worker가 처리한다.

## 3. 논리 큐

작업 종류별 논리 큐 이름은 아래를 기준으로 한다.

| Queue | 용도 | 우선순위 |
| --- | --- | --- |
| `critical` | 사용자 영향도가 큰 고우선 작업 | 높음 |
| `mail` | 메일 발송 | 보통 |
| `sms` | 문자 발송 | 보통 |
| `chat` | 채팅 후처리 | 높음 |
| `notifications` | Push/알림 외부 발송 | 높음 |
| `default` | 일반 비동기 작업 | 보통 |
| `maintenance` | 정리, 백필, 유지보수 | 낮음 |

큐 이름은 로그, metric, DB 상태값에서 동일하게 사용한다.

## 4. 작업 작성 규칙

- 작업 입력은 id 중심으로 넘긴다. 큰 DTO나 파일 본문을 큐 payload에 넣지 않는다.
- 작업은 재시도되어도 데이터가 깨지지 않게 멱등성을 가져야 한다.
- 외부 API 호출은 timeout, retry, 실패 상태 저장 기준을 명시한다.
- 작업 시작/성공/실패 로그에 `traceId` 또는 parent trace id를 남긴다.
- 실패 원인이 사용자 입력 오류인지 외부 장애인지 구분한다.
- 같은 작업을 중복 실행하면 안 되는 경우 DB unique key 또는 distributed lock을 사용한다.

## 5. 상태 테이블 기준

유실되면 안 되는 작업은 상태 테이블을 둔다.

예시 필드:

- `id`
- `channel` 또는 `job_type`
- `status`: `PENDING`, `PROCESSING`, `SENT`, `FAILED`, `CANCELLED`
- `attempt_count`
- `last_error_code`
- `last_error_message`
- `scheduled_at`
- `processed_at`
- `created_at`
- `updated_at`

작업 성공 여부를 로그에만 의존하지 않는다. 운영 화면과 재처리는 DB 상태를 기준으로 한다.

## 6. 운영 기준

- 대기 수, 실패 수, 평균 처리 시간을 metric으로 남긴다.
- 실패 작업은 원인 확인 후 재처리 가능 여부를 판단한다.
- 재처리 명령은 대상 범위, limit, dry-run 옵션을 제공한다.
- maintenance 작업은 사용자 영향도가 낮은 시간대에 실행한다.

## 7. 장애 대응

### 작업 적체

1. 어떤 논리 큐가 적체됐는지 확인한다.
2. 외부 API 장애인지 DB 병목인지 분리한다.
3. worker 동시성 조정 또는 batch 크기 축소를 검토한다.
4. 반복 적체면 작업 분리와 인덱스 보강을 검토한다.

### 실패 급증

1. 실패 코드와 예외 메시지를 그룹화한다.
2. 재시도 가능한 실패와 영구 실패를 분리한다.
3. 코드 수정 후 재처리 범위를 제한해 실행한다.
4. 사용자에게 영향이 있는 실패는 운영 이력 또는 알림 정책과 연결한다.
